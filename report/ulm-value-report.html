01ulm とは — 知識の置き場を4段に分ける

AI コーディングエージェントは「その場の作業」には強いが、前回つかんだコツを次の似た作業へ持ち越せず、毎回同じ落とし穴を踏む。ulm はその「現場の勘所を育てる生もの」の中間層を担う、依存ゼロ（node:sqlite のみ）の CLI + Claude Code プラグイン。

層役割性質
CLAUDE.md常に守るルール常時注入・人が書く
ref人が吟味した正式規範承認済み・安定
beads (bd)課題の構造（依存グラフ）セッション〜プロジェクト
ulm（これ）現場の勘所を育てる「生もの」揺れている知識の中間層

記憶を腐り方で3分類（観測=追記／可変状態=上書き+TTL／仮説候補=育てる）。普段は隠し関連分だけ SessionStart で注入。仮説は inbox に隔離して人間の承認で ref へ昇格。機密の門番は AI でなく機械的ルール。

02検証のやり方

「やりたいことを伝えてしっかりレビューさせ、実リポジトリでシミュレーションして実価値を測る」という依頼に沿い、3つを並行実施した。

レビューA

codex exec（外部LLM）

gpt-5.5 (low) に ulm の実コードを読ませ、「実際の開発現場で価値があるか」を忖度なく評定。read-only sandbox で実行。

レビューB

subagent（独立コンテキスト）

fresh-context の subagent が README/DESIGN/src を読み、temp 環境で init→obs→mine→promote を実走させて挙動を確認しつつ評定。

実証

実リポジトリ・シミュレーション

実在の TTS コードベース irodori で、多セッションの開発ワークフローを再現。観測はすべて実コードに file:line の根拠あり。

測定

A/B テスト

同じ落とし穴タスクを「記憶なし」「記憶あり」の2エージェントに与え（両者ファイル読込み禁止）、回避の質を比較。

両者が「主張通り」と認めた強み

subagent は temp 環境で実際に動かし、次を確認した：

  • 機密ゲートは本物：sk-proj-…／postgres://user:pass@…／password= を投入すると自動 secret 化され、注入・検索・export から機械的に除外。判定に LLM を介さない。
  • 注入無害化が効く：SYSTEM: → ロール:、</user-memory> → [tag] に中和し、データ境界を死守。
  • 人間ゲートが堅い：非対話で approve/promote は --yes 必須。CLAUDE.md や /etc/passwd.md への昇格は機械的に拒否。
  • 差別化が明確：mem0/Letta が「自動で記憶を統合」して漏洩・権威偽装リスクを抱えるのに対し、ulm は「自動採用しない・出自常時表示・inbox 隔離」の逆張り保守設計。

両者が一致して指摘した弱み

指摘誰が本レポートの立場
想起が関連度検索でなく recency 詰め込み（LIKE 部分一致のみ）codexDESIGN §10 で意図的に MVP 非スコープ化した点。記憶増大時の劣化は実在リスク。改善候補の筆頭（FTS/BM25）。
記録が貯まるか（手動 obs add は続かない／自動化が skill 任せ）subagent最大の急所。SessionEnd で自動キャプチャする仕組みが次の一手。
UX 不統一：state set に --global が無い／/tmp で project="tmp" になるsubagentシミュレーション中に実際に踏んだ（後述）。妥当な指摘。

出典：.review/codex-verdict.md、subagent 最終報告。両レビューとも本レポートに生データを保持。

05A/B：記憶が答えを変えた

同じ落とし穴タスクを2エージェントに与えた。両者ともファイル読込み禁止にして、変数を「記憶の有無」だけに絞っている。

テスト1：v1 checkpoint を v3 コードで使いたい（一般知識でも警戒できる例）

✕ 記憶なし
「v1 と v3 は非互換の可能性が高いので避けてください。…互換情報は README やリリースノートで確認するのが確実です。」
ヘッジ止まり — 確認作業を人に丸投げ
✓ 記憶あり
「そのままは不可です。注入記憶上、v2/v3 コードが対応するのは v2 後方互換と v3 のみ。音声生成したいだけならv1 タグ/当時のコードに戻して推論してください。」
確信ある具体策 — v1 タグという解まで提示
強いベースモデルは「バージョン非互換かも」と自力でヘッジできる。だが記憶は、その曖昧なヘッジを出自つきの確定回答＋具体的な対処に引き上げる。

テスト2：v2 VoiceDesign で参照音声が効かない（モデルが推測できないリポ固有の事実）

✕ 記憶なし
「v2 VoiceDesign は参照音声から話者をクローンするモデルではない可能性が高い。参照音声対応の別モデル/API があるか確認を。入力形式・サンプリングレートも見直しを。」
誤誘導 — 別モデル探しへ向かわせる
✓ 記憶あり
「v2 VoiceDesign は use_caption_condition: true だとspeaker 条件が無効化されるため、参照音声で声を真似る用途には効きません。話者模倣が目的なら speaker 条件が有効な v2 base 系を使う。…（normalize_db の注意も付随）」
正確な機構＋正しい対処＋付随 gotcha
ここが ulm のクリーンな勝ち筋。「v2 VoiceDesign は設計上 reference audio を無視する」はモデルの事前知識に無いリポジトリ固有の事実。記憶なしは別モデル探しへ誤誘導するが、記憶ありは config レベルの正解を即答する。

評価は両条件とも同一モデル（codex gpt-5.5, low）で実施。記憶ありには Session 2 の注入ブロック（約3.6KB）だけを前置した。生回答は .review/sim/ab/ に保持。

07正直な限界（誇張しないために）

① 想起は意味検索でない。 現状は recency＋ピン＋project スコープの詰め込みで、LIKE 部分一致しかない。観測が数千件に増えると、古いが重要な知見が埋もれる。mem0/Letta のセマンティック想起に明確に劣る（codex の最大指摘）。
② 記録が貯まるかが生命線。 手動 obs add は続かず、自動化は skill の「お願い」止まり。DB が薄いままだと注入も mine も空回りし、価値を体感する前に忘れられる（subagent の最大懸念）。SessionEnd 自動キャプチャが次の一手。
③ A/B の前提。 強いモデルは一般的なバージョン非互換なら自力で警戒できる。ulm のクリーンな勝ちはリポ固有の事実に限られる（テスト2）。「何でも賢くなる」ではなく「その現場でしか分からない事実を逃さない」ツールと理解すべき。
④ UX の粗。 state set に --global が無く --scope と不統一、git 外（/tmp 等）では project が basename になりゴミ project を生む、mine --project X が global 観測を拾わない、等。シミュレーション中に実際に踏んだ。

08結論

ulm には実価値がある。実在リポジトリの A/B で、記憶は「READMEを自分で確認して」という曖昧なヘッジを、出自つきの正確で実行可能な答えに変えた。とりわけモデルが原理的に知り得ないリポジトリ固有の事実（v2 VoiceDesign が設計上 reference audio を無視する 等）で、記憶なしが別モデル探しへ誤誘導する横で、記憶ありは config レベルの正解を即答した。これは「作業で得たコツを、次の仕事で迷わず使う」という当初の狙いそのものである。

同時に、2人の評価者が一致して突いた限界 ——想起が意味検索でないことと記録が習慣化しにくいこと—— は本物だ。ここを埋めない限り、優れたセキュリティ設計も昇格パイプラインも「空の記憶レイヤー」の上物に留まる。

次の一手（投資対効果の順）

  1. 記録の自動キャプチャ：SessionEnd/Stop hook で、その回の作業から再利用可能な観測を自動抽出して obs add（機密ゲートは既に入口にある）。死のループを断つ最優先策。
  2. 想起の関連度化：SQLite FTS5/BM25 を入れ、SessionStart でタスク文脈に効く観測を上位提示。recency 詰め込みから卒業する。
  3. UX の整流：state set --global、project の安定 ID 化、mine の global 観測取り込み。

評価 62〜72/100。「効く人には強く刺さる、作りの良い MVP」。技術的完成度（依存ゼロ・テスト85件・多層セキュリティ）は十分に高く、残るは行動変容（記録の習慣化）と想起品質という、ツールの“入口と出口”の改善である。
