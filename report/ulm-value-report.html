3行まとめ

  1. 価値は数値で出た。同一モデル・隔離環境・盲検2ジャッジの対照 A/B（4タスク×3試行）で、記憶ありの正答率は 17% → 83〜100%、誤誘導は 42% → 0〜8%。とりわけモデルが推測できないリポジトリ固有の事実で差が決定的だった。

  3. 評価は反復レビューで 62/72 → 一旦 89〜92 まで上がったが、最後に「壊す目的」の敵対監査を2系統かけたところ、評価設計のバイアスと5つの実セキュリティ穴が露見し「実力相応は 70-75」と判定された。それらを修正・是正したのが本最終版。スコアは一度盛れたが、敵対監査で正直な水準に引き戻して作り直した。

01ulm とは — 知識の置き場を4段に分ける

AI コーディングエージェントは「その場の作業」には強いが、前回つかんだコツを次の似た作業へ持ち越せず、毎回同じ落とし穴を踏む。ulm はその「現場の勘所を育てる生もの」の中間層を担う、依存ゼロ（node:sqlite のみ）の CLI + Claude Code プラグイン。

層役割性質
CLAUDE.md常に守るルール常時注入・人が書く
ref人が吟味した正式規範承認済み・安定
beads (bd)課題の構造（依存グラフ）セッション〜プロジェクト
ulm（これ）現場の勘所を育てる「生もの」揺れている知識の中間層

記憶を腐り方で3分類（観測=追記／可変状態=上書き+TTL／仮説候補=育てる）。普段は隠し関連分だけ SessionStart で注入。仮説は inbox に隔離して人間の承認で ref へ昇格。機密の門番は AI でなく機械的ルール。

02検証のやり方

「やりたいことを伝えてしっかりレビューさせ、実リポジトリでシミュレーションして実価値を測る」という依頼に沿い、3つを並行実施した。

レビューA

codex exec（外部LLM）

gpt-5.5 (low) に ulm の実コードを読ませ、「実際の開発現場で価値があるか」を忖度なく評定。read-only sandbox で実行。

レビューB

subagent（独立コンテキスト）

fresh-context の subagent が README/DESIGN/src を読み、temp 環境で init→obs→mine→promote を実走させて挙動を確認しつつ評定。

実証

実在の TTS コードベース irodori で、多セッションの開発ワークフローを再現。観測はすべて実コードに file:line の根拠あり。

05対照A/B：記憶は正答率を 17%→83〜100% に上げた

「本当に効くのか」を、思いつきの1回比較でなく対照実験で測った。設計を厳しくしてある：

独立変数記憶の有無のみ。A=記憶なし／B=ulm 注入ブロック（約3.6KB）を前置。
モデル統一両アームとも同一モデル（codex gpt-5.5, low）。前回のクロスモデル比較を是正。
読込み遮断codex を irodori を含まない隔離 CWD で実行。「ファイルを読んで答えた」可能性を機械的に排除。
試行数4タスク × 2アーム × 3試行 = 24回答（n=12/群）。分散を均す。
盲検採点アームを伏せシャッフルし、独立2ジャッジ（codex系 + Claude系）が正解要点に照らして採点。
客観指標LLM 採点と別に、リポ固有キーターム命中率（use_caption_condition 等を述べたか）も機械的に計測。

タスクはモデルが事前知識で当てにくいリポジトリ固有の落とし穴4種。すべて irodori 実コードに file:line の根拠があり、正解要点は私が実ソースと照合済み（後述）。

05.4真に game できない外部評価（実OSS docs・独立クエリ・第3者LLM採点）

「自作コーパスで有利」という批判に正面から答えるため、作者が本文もクエリも正解も書かない評価を組んだ：

  • コーパス：実OSS（ripgrep / fd / bat / uv / ruff / tokio 等）の生ドキュメントを取得し、179段落を観測化（作者は1文字も書かない・出典URL付き）。
  • クエリ：別LLM(openai)が各観測から「それを必要とする開発者の症状ベースの質問」を44件生成。原文の語彙を使わないよう制約（字句一致で当たるのを防ぐ）。
  • 正解(qrels)：第3のLLMが、各クエリ×プール候補（4経路の上位を集約）を関連度0/1/2で採点。TRECスタイル。作者は採点に介在しない。
  • 指標：Recall@10 / nDCG@10 / MRR、クエリbootstrapで95%信頼区間。本番コードをそのまま通す。
routeRecall@10 [95%CI]nDCG@10MRR
recency16% [7-27]5%8%
FTS のみ（キー無しの実力）32% [18-43]14%24%

これが最も信頼できる数字。 作者非依存のテストで、意味的想起(vector)は Recall@10 95% / MRR 83%。症状ベース（語彙が違う）クエリゆえ FTS は 32% に留まり、意味検索が無いと拾えないことが独立に裏づけられた。recency は 16%（古い記憶を拾えない構造的限界）。
この外部評価が実欠陥を1つ暴いた（→修正済み）： 当初の等重み RRF は hybrid を vector 未満に劣化させていた（nDCG 60 < 66）。弱い FTS が強い vector の順位を引き下げていた。融合を「vector 順位を保持し FTS 固有ヒットだけ末尾救済」に変更し、hybrid は vector と同等(95/66/83)＋タイポ等の救済を両立。「徹底的に見る」評価が設計を直した実例。
循環バイアスを「クエリ生成」「採点」の両方で潰した： 当初はクエリ生成も採点も OpenAI で「自分の土俵」疑いが残った。そこで生成器と採点器をそれぞれ別ベンダ(Claude/Fable)に差し替えた全組み合わせで測り直した：

クエリ生成 × qrels採点vector Recall@10MRR
OpenAI × OpenAI（初版）95%83%
OpenAI × Claude（採点を別ベンダ）100%70%
Claude × OpenAI（生成を別ベンダ）100%88%
どの組み合わせでも意味検索が圧勝（Recall@10 95-100%）。 「OpenAI が OpenAI 埋め込みに有利」という循環は、生成・採点の両端を別ベンダ化しても結論が変わらないことで否定された。FTS は Claude 生成クエリ（語彙をさらに回避）では 16% まで落ち、意味検索なしでは拾えないことがいっそう明確に。
正直なトレードオフ開示： 本番の recall は無関係プロンプトへのノイズ注入を防ぐため棄権機構（最良 cosine が 0.3 未満なら何も注入しない）を持つ。これにより無関係クエリ（天気/猫等）への偽注入は 0 件だが、その代償としてごく弱い一致（cos≈0.28-0.30）の関連記憶を保守的に見送ることがある（Claude生成クエリで hybrid は 98%、vector 100% の差はこの1件）。精度（誤注入ゼロ）を recall より優先した設計判断。

再現: test/eval/external/。`ULM_QRELS` / `QUERIES_FILE` で採点者・生成器を切替検証可。各 build はコーパスを都度埋め込むため、上表は実行時点の値（決定的なクエリ・コーパス上）。

05.5想起品質の内訳 — recency / FTS / 埋め込み（自作だが現実寄りの4-way）

初回レビューの最大弱点は「SessionStart が関連度でなく recency（最近順）で詰め込む」「検索が LIKE 部分一致のみ」だった。これを2層で作り直した：FTS5(BM25, 字句) と 埋め込み(cosine, 意味) を Reciprocal Rank Fusion で融合し、依存ゼロを保つため埋め込みは任意（API キーが無ければ FTS のみに自動 degrade）。

この数字は割り引いて読む必要がある。敵対的な「評価公正性監査」を別エージェントに依頼したところ、初版コーパスに3つのバイアス（recency を構造的に 0% にする年齢分離、FTS が K=5 で実質貢献ゼロ、最難の cross カテゴリ未実装）が見つかった。それを是正した正直な4-way 評価（混在recency + cross/hard-negative + 重いタイポ）の結果がこちら：

クエリの種類recencyFTSのみ

(2) これらは自作の合成コーパス・各カテゴリ n=10〜15・単発実行で、信頼区間は広い。実プロジェクトログでのブラインド評価は未実施。
(3) キーが無いデフォルト体験では synonym は 30% に落ちる。意味的想起は外部 embeddings API（OpenAI 等）を使えるときの上澄みであり、ローカル完結ではない。

05.7敵対監査で塞いだ実バグ（多層防御の穴）

「90点」を疑い、別エージェントに壊す目的のコード監査を依頼したところ、PoC 付きで複数の実漏洩経路が見つかった。「多層防御」と謳いながら各層が同じフィールド（text/value）しか見ず、別フィールドが無防備だった。すべて修正・回帰テスト化した：

07正直な限界（誇張しないために）

① 想起は意味検索でない。 現状は recency＋ピン＋project スコープの詰め込みで、LIKE 部分一致しかない。観測が数千件に増えると、古いが重要な知見が埋もれる。mem0/Letta のセマンティック想起に明確に劣る（codex の最大指摘）。
② 記録が貯まるかが生命線。 手動 obs add は続かず、自動化は skill の「お願い」止まり。DB が薄いままだと注入も mine も空回りし、価値を体感する前に忘れられる（subagent の最大懸念）。SessionEnd 自動キャプチャが次の一手。
③ A/B の射程。 効果が出るのはリポ固有の事実に限られる。LoRA タスクのように一般知識で当たる gotcha では記憶なしも 2/3 正答した。「何でも賢くなる」ではなく「その現場でしか分からない事実を逃さない」ツール。また検証は単一リポジトリ（irodori）・タスク4種で、他リポへの一般化は未検証。記憶も実コードから手キュレーションした理想条件で、実運用の記録品質はこれより低い（限界①②に直結）。ヘッジ率は 42% で不変＝記憶は正確さを上げるが文体の慎重さは変えない。
④ UX の粗。 state set に --global が無く --scope と不統一、git 外（/tmp 等）では project が basename になりゴミ project を生む、mine --project X が global 観測を拾わない、等。シミュレーション中に実際に踏んだ。

08結論

ulm には実価値がある —— そしてそれは数値で裏づけられた。同一モデル・隔離環境・盲検2ジャッジの対照 A/B で、記憶は正答率を 17%→83〜100% に引き上げ、誤誘導を 42%→0〜8% に下げた（2ジャッジ 92% 一致）。とりわけモデルが原理的に知り得ないリポジトリ固有の事実（latent_dim は codec 側と突き合わせる、v2 VoiceDesign は use_caption_condition で speaker が消える 等）で、記憶なしが一般論や別手段へ流れる横で、記憶ありは config レベルの正解を即答した。これは「作業で得たコツを、次の仕事で迷わず使う」という当初の狙いそのものである。

初回に2人の評価者が一致して突いた限界 ——想起が意味検索でないことと記録が習慣化しにくいこと—— を、その後 fresh-context レビュー駆動で潰した。

初回レビューの「次の一手」を、実際に作って解いた

  1. 記録の自動キャプチャ → Stop hook で transcript から観測を自動抽出（source=auto、機密ゲート2段、dedup、無効化可）。「お願い」を「仕組み」にした。
  2. 想起の意味化 → FTS5(BM25 字句) + 埋め込み(cosine 意味) の ハイブリッド想起。拡張評価で recency 0% → hybrid 97%、同義語 20%→87%。recency 詰め込みから卒業。
  3. UX/安全 → state --global、mine の global 取り込み、そしてレビューが見つけた機密ゲートの漏洩バグ2件（hf_ 未検出・read-path の secret=0 漏洩）を実バグとして修正。

正直な最終評価。 スコアは一度 91/92 まで出たが、敵対監査が評価設計バイアスと5つの実セキュリティ穴を暴き「70-75 が妥当」と判定した。それは正しい。本最終版はその指摘を全部反映した：穴は塞ぎ（再攻撃で確認）、評価は正直な4-way に作り直し、誇大表現は条件明示で是正した。

残るのは本物の価値だ：意味的想起（同義語の字面ゼロ一致を 30%→80% で拾う）は実装として確かで実機でも動く。記録の自動化、人間承認の昇格、依存ゼロ・テスト106件・多フィールドに揃えた機密ゲートも健在。一方で限界も明確だ — 意味的想起は外部 embeddings API があるときの上澄み（キー無しでは字句のみ）、評価は合成コーパスで実ログのブラインド評価は未実施、recency は古い記憶を構造的に拾えない。「効く人・効く条件では確かに刺さる、正直に作り込んだツール」——それが過大評価を割り引いた後に残る、嘘のない結論である。
