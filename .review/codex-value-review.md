# レビュー依頼: ulm（user-level memory）の「実際の価値」を厳しく評価してほしい

あなたは AI 開発者ツールに精通した、忖度しない評価者です。このリポジトリ（ulm）の実コードを読み、
「これは実際の開発現場で価値があるのか」を批判的に評価してください。リップサービスは不要。弱点を遠慮なく。

## ulm が解決しようとしている課題（やりたいこと）

Claude Code のような AI コーディングエージェントは「その場の作業」には強いが、前回つかんだコツを
次の似た作業へ持ち越せない。毎回ゼロから同じ落とし穴を踏む。これを解決するための
「ユーザーレベル長期記憶レイヤー」が ulm。知識の置き場を4段に分ける思想:

1. CLAUDE.md — 常に守るルール（常時注入）
2. ref — 人が吟味した正式規範
3. beads(bd) — 課題の構造（依存グラフ・タスク文脈）
4. **ulm（これ）** — 現場の勘所を育てる「生もの」の記憶（揺れている知識の中間層）

ulm は ref の手前。まだ正式ルールにできない経験則を預かり、検証できたものだけを人間の承認で ref へ昇格させる。
記憶を腐り方で3分類（観測=追記/可変状態=上書き+TTL/仮説候補=育てる）。普段は隠し関連分だけ SessionStart で注入。
仮説は遊び場(inbox)で育て人間承認で正式化。機密の門番は AI でなく機械的ルール。

## 評価してほしい観点（各々、根拠を実コードから引いて）

1. **本当に価値があるか**: この「中間層の記憶」は実在の課題を解くか。それとも CLAUDE.md や bd で足りるか。
   どんな開発者・どんなワークフローで効くか／効かないか。
2. **既存との差別化**: mem0 / Letta(MemGPT) / 素の CLAUDE.md / beads と比べた独自性と弱点。
3. **採用障壁**: 開発者が実際に使い続けるか。毎セッション obs add する習慣は根付くか。摩擦は。
4. **設計の妥当性**: 3分類・inbox隔離・人間承認昇格・機械的機密ゲートという設計判断は正しいか。過剰/不足は。
5. **実装の質**: コードは主張通りに動くか。明らかな穴・未完・誇大広告はないか（src/ を実際に読んで）。
6. **致命的な見落とし**: このツールが現場で失敗するとしたら、最大の理由は何か。
